# 変更容易性を改善するリファクタリング計画

作成: 2026-10-05。静的レビューに基づく計画。実装・DB変更・動作検証は未実施。
進捗はこの文書のチェックボックスで管理する。

現行実装と既知の制限は[現行仕様](../apps/web-next/docs/specification.md)、機能追加の進捗は[開発状況](development-log.md)を参照。以下の想定構成・変更後の挙動は未実装の計画。

## 目的と方針

- 登録・更新ルールを通常APIとCSV取込で共有し、仕様変更の修正箇所を減らす。
- 関連更新の完了条件を明示し、途中失敗で不整合を残さない。
- APIの入力・出力・認可を明示し、変更漏れを型とテストで検出する。
- Next.js、NextAuth、Prismaを継続使用し、機能単位の小さな変更で進める。
- 既存APIのパス・レスポンスは原則維持する。認可・検証・検索の修正による挙動変更はPRに記載する。

想定構成（`apps/web-next/src/` 配下）:

| 配置 | 責務 |
|---|---|
| `app/api/**/route.ts` | HTTP入力、認証・認可、業務操作の呼出し、HTTP応答 |
| `lib/server/auth.ts` | 現在ユーザー取得、管理者・所有者の判定 |
| `lib/server/products.ts`, `owned-vehicles.ts` | 業務操作、トランザクション境界、Prismaアクセス |
| `lib/server/queries/` | 型付き検索条件・ソートの構築 |
| `lib/contracts/` | サーバー入力スキーマ、API出力型、共通エラーコード |
| `components/products/`, `owned-vehicles/` | 共通フォーム・表示。フォームとAPI入力の変換は専用関数に分離 |

サーバー専用モジュールがクライアントへ混入しない境界を設ける。通常処理は業務関数がトランザクションを開始し、関連処理には `Prisma.TransactionClient` を渡す。

## 実施順とTODO

順序は R0 → R1 → R2 → R3 → R4 → R5。各段階を独立したPRに分け、完了条件を満たしてから次へ進む。

### R0: 挙動と未決事項の整理

- [ ] APIの操作別に、公開・ログイン必須・所有者限定・管理者限定を表にする。製品作成・編集・削除の権限を既存仕様と照合して確定する。
- [ ] 製品のメーカー＋品番による照合と、同一品番のバリエーションを整理する。一律の一意制約追加は、この決定後に判断する。
- [ ] CSVの重複・空欄・不明種別・部分成功の現行挙動を記録し、維持する挙動と修正する挙動を区別する。
- [ ] 関連更新の途中失敗、タグAND検索＋ページ分割、他ユーザーの操作拒否について回帰テストを用意する。既知の不具合は期待する修正後の挙動を明記する。

完了条件: 権限表・照合規則・成功条件が記録され、実装者が推測せず着手できる。

### R1: API入力・認可・出力の契約（優先度: 高）

- [ ] 現在ユーザー取得と認可を共通化し、製品・構成車両・タグ・保有車両・画像・管理APIの各入口へ適用する。画像の所有者・作成者チェックも含める。
- [ ] 作成・更新・CSV変換後の入力スキーマを定義する。ID、整数価格、日付、enum、空文字・null・省略の意味を明示する。
- [ ] 検証済み入力から保存項目を明示的に構築する。入力の残余プロパティ展開と書込データの `as any` を除く。
- [ ] 一覧・詳細のAPI出力型と変換を定義する。日付はJSONの文字列型として扱い、Prismaの全レコードを契約にしない。
- [ ] 400/401/403/404/409/500の使い分けを統一し、例外メッセージの部分一致による認可エラー判定を除く。

完了条件: 不正入力・未認証・他ユーザー操作をAPIで拒否し、DB項目追加が書込可能項目を自動的に増やさない。

### R2: 業務操作・永続化・トランザクション（優先度: 高）

- [ ] 製品作成・更新＋タグ更新、独立車両の製品紐付け、保有セット＋構成車両登録をサーバーの業務関数へ移す。
- [ ] 製品作成後の紐付けはサーバー操作として提供する。画面からの `PATCH` 呼出しとAPIの `PUT` 実装の不一致も解消する。
- [ ] 独立車両の作成・削除と保有車両本体の更新を同一トランザクションにする。
- [ ] `autoRegisterSetComponents` がトランザクションクライアントを受け取れるようにし、通常登録・CSVとも完了を待つ。
- [ ] CSVはチャンク単位の全成功/全失敗を明示し、成功件数をコミット後に加算する。途中まで成功したチャンクと失敗行を結果で区別する。
- [ ] 製品CSVをPrismaと共通の登録処理へ移行する。日本語のDB enum値とPrisma enum値の変換、作成者、重複判定を揃える。
- [ ] 選択削除・全削除の関連更新も業務関数とトランザクションに集約する。削除対象の範囲はR0の仕様で確認する。
- [ ] Supabase版の重複処理は参照箇所を確認して整理する。認証など残る利用箇所を確認してから依存・環境変数の削除を判断する。

完了条件: 途中失敗で関連データを残さず、成功応答は必要な関連更新の完了後に返る。通常登録とCSVが同じルールを使う。

### R3: セット関係のID化（優先度: 高、既存データ移行あり）

- [ ] 製品構成は中間テーブルを第一候補とし、同じ製品の複数セット所属・構成数量・順序の要否を確定する。
- [ ] 保有構成車両に親保有セットのIDを持たせ、親削除時の構成車両の扱いを確定する。
- [ ] Prismaスキーマへ追加し、既存の品番・備考からの移行スクリプトを作る。実行前に候補・未解決・複数候補の件数を出すドライランを用意する。
- [ ] メーカー＋品番で一意に特定できる関係のみ移行する。名称変更、空の管理ID、同一セット複数購入、バリエーション等の曖昧な関係は一覧化し、推測で確定しない。
- [ ] 新旧関係の読取互換と新規登録時の書込み方針を定め、構成登録・親セット検索・詳細表示をID参照へ切り替える。
- [ ] 再実行しても関係が重複しないことと、製品名・品番・管理ID・備考の編集で関係が変わらないことを確認する。

完了条件: 移行件数と未解決件数を記録し、ID化したデータの関連判定に表示文字列を使わない。

### R4: 検索・ソート・ページ分割（優先度: 高）

- [ ] パラメータを検証し、Prismaの型付き条件を構築する。メーカー・キーワード等はANDで組み合わせ、`OR` の上書きを除く。
- [ ] タグANDを「指定タグをすべて持つ」として共通化する。タグなし、余分なタグあり、除外タグ、カテゴリ別「なし」の組合せも扱う。
- [ ] 保有車両のカテゴリ別「なし」をAPIまで接続し、製品未紐付け車両を含めるか仕様に記載する。
- [ ] 名称・品番・分類をサーバーでソートし、同値時はIDで順序を確定する。製品/独立車両の表示値を用いる方式は実装前に決める。
- [ ] 絞込み → ソート → ページ分割の順に処理し、件数取得も同じ条件を使う。画面の取得後ソート・APIの取得後フィルタを除く。

完了条件: 2ページ以上のデータで順序・総件数・条件の組合せが正しく、製品と保有車両のタグANDの意味が一致する。

### R5: フォーム・型の重複解消（優先度: 中）

- [ ] 製品・保有車両の共通フォームを抽出し、新規/編集固有の初期値・遷移をページ側に残す。
- [ ] フォーム値とAPI入力の変換を共有する。0円、項目のクリア、空の実車情報、画像・タグ更新を確認する。
- [ ] 一覧・詳細・管理画面の独自型をR1のAPI出力型へ移行し、必要な表示用型を `types/domain.ts` で共有する。
- [ ] API呼出しのエラー処理を共通化し、保存失敗を利用者に伝える。

完了条件: 共通項目の追加・検証変更を、新規/編集の両画面で重複実装せず反映できる。

## 検証・デプロイ・データ移行

- 各PRで対象の回帰テスト、型チェック、lint、ビルドを実施し、実行コマンドと結果を記録する。コマンドは `apps/web-next` で1操作ずつ実行する。
- 既存スクリプト: `npm run type-check`、`npm run lint`、`npm run build`。単体テストは `npm run test -- --run`。テスト用DBは本番と分離する。
- DB変更は [スキーマ管理ガイド](database-schema-management.md) に従う。現状は `db push` 方式で、migrateの運用は未導入。移行履歴を導入する場合は既存DBのベースラインと適用手順を別途決める。
- R3はバックアップ → 追加スキーマ適用 → 互換コード公開 → 移行ドライラン/実行 → 件数照合 → ID読取へ切替の順。各時点のロールバック方法と書込み競合対策を実装時に記録する。
- `DATABASE_URL` / `DIRECT_URL` の対象環境を確認し、Prismaクライアントを再生成する。ビルド時の `prisma generate` だけではDBスキーマは更新されない。
- 旧カラム・互換処理の削除は、移行完了とロールバック期間終了後の別PRにする。未解決データがある間は互換を残す。
- 実際の適用コマンド、環境変数の追加/廃止、移行スクリプトのパス、復旧手順は [デプロイ手順](../apps/web-next/docs/deployment-setup.md) に追記する。
